## Packaging, Distribution & Cross-Platform

**Overlap with existing FA:** Partial overlap with FA-1 only: both touch src-tauri/src/bin/headless.rs, but FA-1 is about the daemon's functional completeness ('policy-only stub'), while this dimension is about that same binary never being compiled/tested by CI and not actually compiling on Windows. None of FA-1..5 address CI cross-platform coverage, release/bundling automation, or the workspace/Cargo.lock split — this is a genuinely distinct axis.

**Proposed goal:** Make the daemon and desktop bundle actually compile, get unit-tested, and ship via automation on every OS tauri.conf.json already claims to target (Windows/Linux/macOS), not just the author's Mac.

**Current state.** Two Rust manifests, no workspace tying them together: root Cargo.toml (repo root, no [workspace] table — grep confirmed) builds the `neurobrowser` lib crate; src-tauri/Cargo.toml (no [lib] section at all — only a default `main.rs` bin plus a feature-gated `[[bin]] neurobrowser-headless` at src-tauri/Cargo.toml:13-16, required-features=["headless"]) builds the Tauri desktop app. Each has its own Cargo.lock (Cargo.lock, src-tauri/Cargo.lock both exist on disk). .github/workflows/ci.yml is the only CI file (confirmed via `find .github -type f`) and has 3 jobs: `check` (ubuntu-latest, ci.yml:16-38, only touches the root manifest: fmt/clippy/test/release-build), `tauri` (macos-latest ONLY, ci.yml:40-69, runs `npm run build` + `cargo check --manifest-path src-tauri/Cargo.toml` with no --features flag at all), and `guards` (ubuntu-latest, grep-based checks). No job ever runs on windows-latest or ubuntu-latest against src-tauri, and no job ever passes --features headless, so src-tauri/src/bin/headless.rs — the FA-1 daemon deliverable — is never compiled or unit-tested by CI in any configuration; its 4 unit tests (headless.rs:398-502) never run. Independently, headless.rs itself has real Windows-portability bugs: it unconditionally imports and calls `tokio::net::UnixListener` (headless.rs:43, :195) and unconditionally uses unix-only signal handling in `wait_for_signal` (headless.rs:235-243, `tokio::signal::unix::{signal, SignalKind}`), contradicting the file's own doc comment claiming a 'local TCP on non-Unix' fallback (headless.rs:1-12). Only the later chmod call is correctly gated (`#[cfg(unix)]` at headless.rs:213, restricting the socket to 0600). This exact defect is already self-diagnosed and still open in the repo's own docs/goals/optimization-backlog-2026-07-20.md:171-174 ('headless.rs unconditionally uses Unix-only APIs...cargo check --features headless cross-compiled to a Windows target succeeds' is the stated, unmet target metric). No release/bundling workflow exists anywhere in .github/ (`find . -iname '*release*'` returned nothing); src-tauri/tauri.conf.json declares `"bundle": {"targets": "all", ...}` plus a Windows codesigning stanza (certificateThumbprint/digestAlgorithm/timestampUrl) that nothing in CI ever exercises — no job runs `tauri build`/`cargo tauri build`, only `cargo check`. Dev tooling hardcodes unix paths: verify.sh:14 and package.json:10 (`smoke:desktop` script) both set `CARGO_TARGET_DIR=/tmp/neurobrowser-tauri-target`, and verify.sh is a bash script (verify.sh:1, `#!/usr/bin/env bash`) — the project's own canonical pre-completion verify chain cannot run on stock Windows. On the positive side: no hardcoded `/Users/` paths and no un-parameterized `/tmp/` literals exist in any Rust source (`rg` across --type rust was clean except the two verify-tooling files above); `std::env::temp_dir()` is used correctly (headless.rs:183); and the daemon does attempt a genuine TCP fallback when the Unix socket bind fails (headless.rs:195-206) — the cross-platform intent is present, just not fully gated/compiled/CI-verified. A parallel macOS-only native lane exists (NeuroBrowser.xcodeproj at repo root + extract_pdf.swift) but docs/adr/ADR-001-react-tauri-primary.md designates it a 'parity and native-ceiling lane,' not the shipping target, so it doesn't itself count against cross-platform intent.

**Gaps:**

- **[P0]** Headless daemon binary is never compiled or unit-tested by CI on any OS, and is confirmed broken on Windows — `src-tauri/src/bin/headless.rs:43`
  - _evidence:_ headless.rs:43 unconditionally `use tokio::net::{TcpListener, UnixListener}`; :195 unconditional `UnixListener::bind`; :235-243 unix-only `wait_for_signal`. CI's only src-tauri-touching job (.github/workflows/ci.yml:68-69) runs `cargo check --manifest-path src-tauri/Cargo.toml` with no `--features headless`, so this file (default=[] gates the bin) is never even parsed by CI, on macos-latest (the only OS that job runs on) or anywhere else; the root `check` job (ci.yml:16-38) never touches src-tauri at all. Repo's own docs/goals/optimization-backlog-2026-07-20.md:171-174 already flags this as unresolved.
- **[P0]** No release/bundling automation exists anywhere; tauri.conf.json's declared bundle targets are never exercised — `src-tauri/tauri.conf.json:11`
  - _evidence:_ tauri.conf.json:11-25 declares `"bundle": {"targets": "all", ...}` plus a Windows signing stanza (certificateThumbprint/digestAlgorithm/timestampUrl), but `find . -iname '*release*'` under the repo returns nothing and .github/ contains only ci.yml, whose only src-tauri step is `cargo check` (ci.yml:68-69) — never `tauri build`/`cargo tauri build`. No automated path produces a distributable binary/installer for any platform.
- **[P1]** CI's Tauri job runs on macos-latest only; Linux and Windows builds of the desktop crate are entirely unverified — `.github/workflows/ci.yml:42`
  - _evidence:_ ci.yml:42 `runs-on: macos-latest` is the only job that ever builds/checks src-tauri; the two ubuntu-latest jobs (ci.yml:18, :73) never touch src-tauri. Tauri v2's `wry`/`tauri-runtime-wry` deps require system packages (webkit2gtk-4.1-dev, libgtk-3-dev, etc.) on Linux that are installed nowhere in ci.yml — a Linux contributor or a hypothetical ubuntu CI job would fail before reaching any Rust code, and no windows-latest job exists to catch the Windows compile break in gap #1.
- **[P1]** No [workspace] links root and src-tauri crates; two independent Cargo.lock files can drift — `Cargo.toml:1`
  - _evidence:_ Root Cargo.toml (lines 1-30) has no `[workspace]` table (grep confirmed); src-tauri/Cargo.toml:19 depends on `neurobrowser = { path = ".." }` as a separate, un-workspaced crate. Both Cargo.lock and src-tauri/Cargo.lock exist on disk as independent lockfiles. CI's own rust-cache config (ci.yml:50-52) treats them as two separate workspaces (`. -> target`, `src-tauri -> src-tauri/target`), doubling build-cache footprint and permitting the shared lib's transitive-dep versions to diverge between the two lockfiles.
- **[P2]** src-tauri has no [lib] target, structurally blocking Tauri's standard iOS/Android mobile scaffold despite shipping iOS icon assets — `src-tauri/Cargo.toml:1`
  - _evidence:_ src-tauri/Cargo.toml has no `[lib]` section (confirmed) and `find src-tauri/src -name lib.rs` returns nothing — only main.rs plus the feature-gated headless bin exist. Tauri v2's mobile targets (`tauri android/ios init`) require a cdylib/staticlib lib crate with a `#[tauri::mobile_entry_point] run()`, which this layout cannot support without refactoring, despite src-tauri/icons/ios/*.png already being present with no corresponding build target.
- **[P2]** Project's own canonical verify script hardcodes unix-only paths and a bash shebang, so it cannot run on stock Windows — `verify.sh:14`
  - _evidence:_ verify.sh:1 `#!/usr/bin/env bash`; verify.sh:14 `CARGO_TARGET_DIR=/tmp/neurobrowser-tauri-target cargo check --manifest-path src-tauri/Cargo.toml`. package.json:10 (`smoke:desktop` script) hardcodes the identical `/tmp/neurobrowser-tauri-target` path. Neither /tmp nor bash-style env-var-prefix invocation exists on stock Windows (cmd.exe/PowerShell) without WSL/git-bash.

**Top actions:**

- (high leverage) Gate the Unix-only APIs in headless.rs (UnixListener import/bind, unix signal wait) behind #[cfg(unix)] with a #[cfg(windows)] alternative (e.g. tokio::signal::ctrl_c()), matching the module's own documented cross-platform claim. — `src-tauri/src/bin/headless.rs`
- (high leverage) Add a windows-latest and a properly-provisioned ubuntu-latest job to ci.yml that runs `cargo check --manifest-path src-tauri/Cargo.toml --features headless` (and `cargo test` for it), so the daemon binary and its 4 existing unit tests actually execute somewhere other than never. — `.github/workflows/ci.yml`
- (high leverage) Add a tag-triggered release workflow (e.g. tauri-apps/tauri-action) that runs `tauri build` for the targets already declared in tauri.conf.json and uploads the resulting bundles as CI artifacts/GitHub Release assets. — `.github/workflows/ci.yml`
- (med leverage) Add a root [workspace] with members [".", "src-tauri"] to collapse the two independent Cargo.lock files/target dirs into one, and replace the hardcoded /tmp/ CARGO_TARGET_DIR overrides in verify.sh and package.json with a portable default (e.g. unset, or std::env::temp_dir()-derived). — `Cargo.toml`

## State, Concurrency & Data Model

**Overlap with existing FA:** Partial overlap with FA-3, which already lists "durable policy audit log" as a remaining item - my persistence gap is broader (applies to all session/worker/agent-memory state, not just the policy audit log). Partial overlap with FA-1's "daemon is a policy-only stub" framing, but FA-1 is about making the daemon callable at all; the dead worker/observation state machine (gap 3 below) is a distinct data-model completeness problem layered on top of that. No existing FA covers the concurrent-run corruption risk (gap 1) or the orphaned-worker/close_page cascade (gap 4) - these are net-new to this dimension.

**Proposed goal:** Make session/agent state provably consistent under concurrency and durable across restarts: one agent runs one turn at a time, every session/worker/memory mutation survives a crash, and no modeled state machine ships without a live caller exercising it.

**Current state.** All mutable state uses std::sync::Mutex with narrow, non-await-spanning critical sections, and lock-acquisition order is consistent within each file (page_counter/agent_config are always locked-and-released before sessions is locked in session/mod.rs:76-99 and :195-199), so no cross-Mutex deadlock pattern was found. Layers: SessionManager holds sessions/agent_config/page_counter (session/mod.rs:9-17); ReActAgent holds five independent Mutexes - config/provider/tool_registry/state/memory (agent/mod.rs:60-66); BrowserEngine holds state/tool_registry (browser/mod.rs:86-92); the Tauri-side BrowserRuntimeRegistry holds pages/pending/active_page (src-tauri/src/runtime.rs:432-437). Every lock scope read is released before any .await (agent/mod.rs:141-148 resets state in a dropped block before build_context().await; the provider Arc is cloned out of its guard in one statement at agent/mod.rs:168; request_json in runtime.rs:608-636 never holds pages/pending locks across the oneshot .await). That part is disciplined.

What is missing is enforcement of the invariants the state model implies. (1) Nothing prevents two concurrent runs on the same Arc<ReActAgent>: ask and start_agent_run in src-tauri/src/main.rs (lines 299-361 and 383-423) both call page.agent.execute_with_policy(...) on a handle obtained from SessionManager::get_page, which only holds the sessions lock long enough to clone the handle (session/mod.rs:101-110) - there is no busy/run-exclusivity flag anywhere on ReActAgent. (2) There is zero persistence anywhere in the tree - a repo-wide grep for fs::write|serde_json::to_writer|sled|rusqlite|persist returned no hits - so SessionManager, AgentMemory (episodic+semantic, agent/memory.rs), and pending_approvals (main.rs:20-32) are pure process memory. (3) An entire modeled subsystem - workers, cross-worker observations, inbox (session/mod.rs:184-337, agent/worker.rs) - is exercised only by tests/workers.rs; main.rs's invoke_handler list (652-677) has no spawn_worker/send_message command and headless.rs's dispatch() (299-363) has no matching branch. (4) close_page (session/mod.rs:136-156) never touches session.workers, so a worker pinned to a closed page is silently orphaned. (5) AgentMetrics is one process-global OnceLock (agent/mod.rs:24-28, observability.rs:73-83) conflating every session/page/agent with no per-session attribution.

**Gaps:**

- **[P0]** No run-level exclusivity on ReActAgent: concurrent execute_with_policy calls on the same Arc<ReActAgent> interleave writes to the shared AgentState (conversation/tool_results/iterations), corrupting cross-run context fed back into the LLM. — `src/agent/mod.rs:141`
  - _evidence:_ agent/mod.rs:60-66 defines no busy/exclusivity field; :141-148 clears conversation/tool_results/iterations at the top of every run with no guard; src-tauri/src/main.rs:299-361 (ask) and :383-423 (start_agent_run) both call page.agent.execute_with_policy on the same handle, and get_page (session/mod.rs:101-110) releases the sessions lock immediately after cloning it, so nothing serializes the two commands.
- **[P0]** Zero persistence anywhere: SessionManager, AgentMemory (episodic+semantic), and pending_approvals are process-memory-only, so a crash or restart discards every session, conversation, audit event, and in-flight approval. — `src/session/mod.rs:9`
  - _evidence:_ Repo-wide grep for fs::write|serde_json::to_writer|sled|rusqlite|persist across src/ and src-tauri/ returned no hits; session/mod.rs:9-17 (Mutex<HashMap> only), agent/memory.rs (plain in-memory Vec-backed EpisodicMemory/SemanticMemory), src-tauri/src/main.rs:20-32 (pending_approvals: Mutex<HashMap> with no backing store).
- **[P1]** Worker/cross-worker-observation state machine (spawn_worker, record_observation, send_message, drain_inbox) has no production caller - it is exercised only by tests/workers.rs, so its concurrency behavior under a real multi-worker run has never been observed. — `src/session/mod.rs:188`
  - _evidence:_ session/mod.rs:188-337 implements the full API; grep for spawn_worker/record_observation/send_message/drain_inbox across src/ and src-tauri/ only matches the definitions and tests/workers.rs; src-tauri/src/main.rs's invoke_handler! list (652-677) exposes only read-only list_workers/get_worker; src-tauri/src/bin/headless.rs's dispatch() (299-363) has no worker-related method at all.
- **[P1]** close_page does not cascade into session.workers: a worker whose pinned_page_id references the closed page is left orphaned with no cleanup, cancellation, or reassignment. — `src/session/mod.rs:136`
  - _evidence:_ session/mod.rs:136-156 mutates only session.pages and session.active_page; spawn_worker's page-pinning logic at :204-216 is the only place pinned_page_id is validated, and nothing re-validates or clears it when the underlying page later disappears.
- **[P2]** AgentMetrics is a single process-global OnceLock singleton shared by every session/page/agent, so per-tool and per-request counters conflate unrelated sessions with no way to attribute activity to a specific session or page. — `src/agent/mod.rs:24`
  - _evidence:_ agent/mod.rs:24-28 (static GLOBAL_METRICS: OnceLock<AgentMetrics>, one instance for the whole process); observability.rs:73-83 (AgentMetrics's tool_call_counts is a flat HashMap<String,u64> with no session/page key).
- **[P2]** page_counter and session/worker ids are process-lifetime-only (in-memory usize / uuid generated fresh each run) with no durable reconciliation, so identifiers are not stable across a restart even though nothing else in the system expects that yet. — `src/session/mod.rs:16`
  - _evidence:_ session/mod.rs:16 (page_counter: Mutex<usize>) and :77-81 (increment with no persisted high-water mark) - combined with gap 2's total lack of persistence, a restart silently resets page ids to 0.

**Top actions:**

- (high leverage) Add a per-agent run-exclusivity guard to ReActAgent (e.g. an AtomicBool/try_lock "busy" flag checked at the top of execute_with_policy) so a second concurrent call on the same agent is rejected or queued instead of interleaving state writes. — `src/agent/mod.rs`
- (high leverage) Introduce a minimal durable store (sqlite or sled) behind SessionManager's existing API for sessions/workers and behind ReActAgent for episodic memory + pending_approvals, so the interior-mutability contract callers already use doesn't change. — `src/session/mod.rs, src/agent/memory.rs, src-tauri/src/main.rs`
- (med leverage) Wire close_page to cascade into session.workers (cancel or unpin any worker whose pinned_page_id matches the closed page) and add at least one live caller (a spawn_worker/drive_worker Tauri command or headless dispatch branch) so the worker/observation subsystem is exercised outside tests. — `src/session/mod.rs:136-223, src-tauri/src/main.rs, src-tauri/src/bin/headless.rs`
- (low leverage) Scope AgentMetrics per session/page (add a session_id or page_id dimension to tool_call_counts) instead of one process-global singleton, so metrics are attributable once multiple sessions run concurrently. — `src/agent/observability.rs, src/agent/mod.rs:24-28`

## Observability & Diagnostics

**Overlap with existing FA:** Partial overlap with FA-4 ("tracing spans... half-wired") and FA-3 ("durable policy audit log" remaining gap). Neither FA names the specific dead span-builder functions, the discarded PolicyDecision reasons/risk_flags, or the structured ToolError type with zero production call sites -- this dimension makes those two backlog bullets concrete and adds net-new findings (dead ToolError, missing token-usage plumbing, unexposed AgentMetrics, silent Tauri command surface) that neither FA-3 nor FA-4 currently itemizes.

**Proposed goal:** Make a failed or blocked run diagnosable from logs/metrics alone, without reading return-value plumbing or source code.

**Current state.** A structured observability module exists (src/agent/observability.rs, 148 lines: CorrelationContext, llm_call_span/tool_call_span/agent_iteration_span span builders, AgentMetrics with atomic counters + MetricsSnapshot) but it is almost entirely disconnected from the code it was built to instrument. Across the whole src/ tree (4,663 lines) there are only 16 tracing:: call sites total, and 10 of those are in one file (src/browser/mod.rs:158-262, HTTP/navigation logging in the read-only scraper engine). The 698-line ReAct loop (src/agent/mod.rs::execute_with_policy / execute_approved_tool, lines 132-454) -- the actual product loop covering LLM calls, tool dispatch, and policy decisions -- has zero tracing:: calls; it only touches observability via three counter increments (metrics().record_request() at mod.rs:164, record_tool_call_named at mod.rs:310/543, record_error at mod.rs:343/547). src/agent/policy.rs (427 lines, ActionPolicy::evaluate) has zero tracing calls anywhere despite computing Allow/Block/RequireApproval decisions with reasons and risk_flags on every tool call. The Tauri desktop binary src-tauri/src/main.rs initializes a subscriber (tracing_subscriber::fmt().with_env_filter("neurobrowser=info").init(), line 631) but itself contains zero tracing:: calls across ~680 lines and 23 #[tauri::command]s. The headless daemon (src-tauri/src/bin/headless.rs) has 5 tracing calls, all for socket bind/accept/connection-close errors -- no per-request logging of dispatched methods or policy outcomes.

**Gaps:**

- **[P0]** The three span-builder functions in observability.rs (llm_call_span, tool_call_span, agent_iteration_span) and CorrelationContext are fully implemented with correlation IDs and span_type tags but have zero call sites anywhere outside their own definitions -- confirmed via `rg -n "llm_call_span|tool_call_span|agent_iteration_span|CorrelationContext" src/` which returns only the definition lines themselves. — `src/agent/observability.rs:46`
  - _evidence:_ grep across all of src/ shows no call site for llm_call_span (line 46), tool_call_span (line 55), agent_iteration_span (line 64), or CorrelationContext::new (line 15) anywhere in src/agent/mod.rs, the actual LLM-call and tool-dispatch loop that needed them.
- **[P0]** ActionPolicy::evaluate computes a PolicyDecision (outcome + reasons + risk_flags) on every tool call, but the decision is never logged and never persisted -- the daemon's policy.snapshot handler claims to capture 'the last 5 policy decisions' but only returns the current policy config, and the Tauri ask command collapses reasons/risk_flags into a single generic string before it reaches the user. — `src-tauri/src/bin/headless.rs:349`
  - _evidence:_ headless.rs:349-356 policy.snapshot handler comment says 'capture the current policy + the last 5 policy decisions into a structured payload' but the code only does `serde_json::to_value(&*policy)` -- no decision history exists anywhere to capture. Separately, src-tauri/src/main.rs:348-354 turns AgentRunResult into AskResult{response, tools_used, iterations}, discarding decision.reasons and decision.risk_flags computed in src/agent/policy.rs:249-329 before returning to the caller.
- **[P1]** ToolError (the one structured error type in the codebase -- code/message/details/retryable, serde + thiserror wired, 14 dedicated unit tests) has zero production construction sites; every real browser/tool failure instead flows as an untyped String through BrowserInterface's Result<_, String> methods and ToolResult{success:bool, result:String}. — `src/tools/errors.rs:12`
  - _evidence:_ `rg -n "ToolError::" src/` returns no hits outside errors.rs's own impl block; tests/error_types.rs exercises the type in isolation (14 tests) but src/tools/mod.rs's BrowserInterface trait (lines 62-75) and browser/mod.rs's tool implementations only ever return plain String errors, so no caller or log line can ever see an error code, a details payload, or a retryable flag.
- **[P1]** AgentMetrics.total_tokens has a record_tokens() method but zero call sites, and the root cause is structural: AiResponse has no usage/token-count field at all, and every provider's response parser (Anthropic/OpenAI/Ollama) discards the API's usage object -- so token/cost visibility is impossible today regardless of wiring effort at the metrics layer. — `src/providers/mod.rs:23`
  - _evidence:_ src/providers/mod.rs:23-28 AiResponse struct has only content/reasoning/tool_calls/finish_reason -- no usage field; src/providers/anthropic.rs's extract_text (lines 68-83) reads only json["content"], never json["usage"]; `rg -n "record_tokens" src/` shows only the observability.rs:90 definition, no callers.
- **[P2]** AgentMetrics is recorded into (record_request/record_tool_call_named/record_error) but its only reader, snapshot(), has zero call sites anywhere in the codebase -- no Tauri command, no daemon method, no CLI ever exposes the accumulated counters to an operator. — `src/agent/observability.rs:109`
  - _evidence:_ `rg -n "\\.snapshot\\(\\)" src/` shows only browser-page snapshot() calls (unrelated PageSnapshot type); MetricsSnapshot / AgentMetrics::snapshot has no caller. src-tauri/src/main.rs's invoke_handler list (lines 652-676, 23 commands) has no get_metrics/health command.
- **[P2]** The Tauri desktop binary initializes a tracing subscriber but contains zero tracing:: calls of its own across ~680 lines and 23 commands -- every command (ask, navigate, click, submit_approval, etc.) is a black box beyond whatever the library happens to log underneath it (which, per the loop gap above, is nothing for agent/policy code). — `src-tauri/src/main.rs:631`
  - _evidence:_ `rg -n "tracing::" src-tauri/src/main.rs` returns 0 matches even though line 631 calls tracing_subscriber::fmt().with_env_filter("neurobrowser=info").init(); the subscriber has nothing app-level to display.

**Top actions:**

- (high leverage) Add #[tracing::instrument] (or manual info_span!/enter) at the top of execute_with_policy and execute_approved_tool in src/agent/mod.rs, using the already-built llm_call_span/tool_call_span/agent_iteration_span/CorrelationContext helpers from observability.rs instead of leaving them dead -- this alone makes the ReAct loop's LLM calls, tool dispatch, and per-iteration progress visible under RUST_LOG=info for the first time. — `src/agent/mod.rs`
- (high leverage) Log every PolicyDecision at the point it is produced in src/agent/policy.rs::evaluate (or immediately at its two call sites, agent/mod.rs:242 and headless.rs:151) with tracing::info!(outcome, reasons, risk_flags, tool_name) so blocked/approval-required calls are visible server-side even when the client-facing response has been flattened to a generic string. — `src/agent/policy.rs`
- (med leverage) Add a metrics/health surface: a get_metrics Tauri command and a metrics or policy.decisions daemon method that call AgentMetrics::snapshot() (already implemented, just uncalled) so an operator can read request/error/per-tool counts without attaching a debugger. — `src/agent/observability.rs`
- (med leverage) Route real BrowserInterface/tool failures through ToolError instead of raw String (start with the browser/mod.rs no-op/error paths), so retryable and code survive to the caller instead of being flattened -- this also gives the 14 existing ToolError unit tests actual production relevance. — `src/tools/errors.rs`

## Configuration and Secrets

**Overlap with existing FA:** Partial overlap with FA-1 (daemon-wiring gap, "the socket-authz follow-up", "NB-3 credential conventions" — explicitly named in docs/goals/focus-areas-2026-07-20.md and docs/specs/programmatic-surface-design-2026-07-20.md:82) and with FA-3 (fail-open policy default, durable audit log). The base_url dead-field bug, the per-run-budget hardcoding, and the RUST_LOG no-op are net-new findings not mentioned in any existing FA, ANALYSIS.md, or docs/goals/*.md.

**Proposed goal:** Make every credential, endpoint, and per-run budget in NeuroBrowser configurable from one legible surface (env var today, config file/CLI later) instead of scattered hardcoded constants and dead config fields.

**Current state.** Config is env-var-only and scattered, not centralized. The only place that reads provider env vars is `provider_config_for()` in `src-tauri/src/main.rs:97-135` (Tauri desktop app): `OPENAI_API_KEY`/`OPENAI_MODEL` (101,103), `ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL` (109,111-112, default `claude-3-5-sonnet-latest`), `OLLAMA_BASE_URL`/`OLLAMA_MODEL` (119-120, default `http://localhost:11434`), `CUSTOM_PROVIDER_API_KEY`/`_BASE_URL`/`_MODEL` (126-130). There is no `src/config.rs` or config-file/CLI-flag mechanism anywhere in the repo (`find -iname '*config*'` under `src/` returns nothing; no `clap`/`toml`/`figment` dependency in `Cargo.toml`). The Anthropic key is read safely: `api_key: Option<String>` (src/providers/mod.rs:77) never defaults to a literal, is passed via the `x-api-key` header (src/providers/anthropic.rs:104) rather than a URL/query string, is never echoed back across the Tauri IPC boundary (`set_provider` returns only `ProviderSelectionResult{provider,model,configured}`, main.rs:71-76,608-625 — no `ProviderConfig`/key ever crosses to the JS frontend), `.env`/`.env.local` are gitignored (.gitignore:23-24), and `rg` over the repo (excluding .git) found zero literal API-key-shaped secrets committed. ## Reliability & Fault-Tolerance (panic/error surfaces, timeouts, cancellation, retries, poisoned-lock recovery, partial-failure handling)

**Overlap with existing FA:** Partial, not primary. FA-4 (ReAct loop quality) notes 'tracing spans + memory + streaming half-wired' — the dead `execute_with_timeout` found here is the concrete instance of that streaming-half-wired claim, but FA-4's framing is about loop *quality* (native tool calls, plan/reflect, selectors), not about the run being uncancellable/unbounded. FA-2 (engine honesty) covers BrowserEngine's no-op click/type/scroll tools, which is adjacent to but distinct from the blocking-HTTP-client issue found in the same file's `navigate`. No existing FA addresses cancellation, wall-clock timeouts, poisoned-lock recovery, or retry/backoff semantics as such — this is a distinct sixth dimension.

**Proposed goal:** Make failure bounded and recoverable: an in-flight agent run can always be cancelled and always has a wall-clock deadline, a panic in one session/page can't permanently brick shared state for the whole process, and error metadata that claims retry semantics (retryable, RateLimited) is either honored by real backoff or removed.

**Current state.** The codebase is disciplined about propagating expected errors as Result<_, String> (session/mod.rs, runtime.rs, main.rs commands almost all return Result and use `?`), and tool-call failures inside the ReAct loop are caught and fed back to the model as an 'Error: ...' string rather than crashing (src/agent/mod.rs:296-303). Providers each set a 30s reqwest timeout (src/providers/anthropic.rs:16-19, openai.rs:16-19, ollama.rs:22-25). However, none of that adds up to actual fault tolerance for a real page/network/model failure: (1) there is no wall-clock deadline or cancellation on an agent run once started — `execute_with_timeout` is fully implemented (src/agent/streaming.rs:78-104) but has zero callers outside its own file (verified via grep), and `start_agent_run`/`ask` in src-tauri/src/main.rs:383-400,299-318 call `execute_with_policy` directly with a bare `.await`; `cancel_agent_run` (main.rs:453-475) only deletes a pending-approval map entry and cannot touch a run that is mid-loop. (2) Every shared-state store (`SessionManager` in src/session/mod.rs:43,46,64,77,83,93,102,115,126,137 and `BrowserRuntimeRegistry` in src-tauri/src/runtime.rs, 17 occurrences) uses `std::sync::Mutex::lock().unwrap()` with zero poison-recovery anywhere in the repo (`rg 'into_inner|clear_poison|PoisonError'` returns nothing) — one panic while holding any of these locks bricks that store's mutex for the rest of the process's life. (3) `ToolError.retryable` (src/tools/errors.rs:9,27,54-57) and `ProviderError::RateLimited` (src/providers/mod.rs:14-15, set on HTTP 429 in anthropic.rs:111-113) exist as retry-classification metadata but nothing in the codebase ever retries — `rg 'retry|backoff'` outside errors.rs/tests turns up nothing, and `provider.complete(...).await.map_err(...)?` (agent/mod.rs:176-182) aborts the whole run on the first provider error regardless of its retryable-ness; tests/error_types.rs even asserts the flag's *value* in isolation (12+ assertions) without ever exercising a retry. (4) `BrowserEngine::navigate` (src/browser/mod.rs:153-199) calls a *blocking* reqwest client directly inside an `async fn` with no `spawn_blocking` (`http_client: reqwest::blocking::Client`, mod.rs:91,162), which can stall a Tokio worker thread for up to its 30s timeout. (5) `TauriBrowserRuntime::wait_for_navigation` (src-tauri/src/runtime.rs:759-761) converts a page-load timeout into `Ok(())` via `.or_else(|_| Ok(()))`, and its callers (click/submit_form/keypress, runtime.rs:685-725) additionally discard that result with `let _ =`, so a real page-load stall is silently treated as success.

  - _evidence:_ wait_for_navigation (runtime.rs:759-761): `self.wait_for_ready(3_000).await.or_else(|_| Ok(()))` swallows the 3s timeout error unconditionally. Callers click/submit_form/keypress (runtime.rs:685-691, 700-706, 719-725) additionally discard the already-swallowed result with `let _ = self.wait_for_navigation().await;`, so a genuinely stalled/failed page load is indistinguishable from a fast successful one to every caller.

**Top actions:**

- (high leverage) Wire the existing execute_with_timeout (src/agent/streaming.rs:78) into start_agent_run/ask, and give cancel_agent_run a real cancellation token or AbortHandle over the spawned run so a stuck loop can actually be stopped, not just its pending-approval entry removed — `src-tauri/src/main.rs`
- (high leverage) Replace `.lock().unwrap()` in SessionManager and BrowserRuntimeRegistry with `.unwrap_or_else(|e| e.into_inner())` (or migrate to parking_lot::Mutex, which never poisons) so one panic can't permanently brick shared session/page state for the process's remaining life — `src/session/mod.rs and src-tauri/src/runtime.rs`
- (med leverage) Either wire ToolError.retryable / ProviderError::RateLimited into a real bounded retry-with-backoff around provider.complete() and tool.execute(), or remove the fields so error-handling code doesn't advertise resilience it doesn't have — `src/tools/errors.rs and src/agent/mod.rs:176-182`
- (med leverage) Move BrowserEngine::navigate off reqwest::blocking::Client (switch to an async reqwest::Client, or wrap the blocking call in tokio::task::spawn_blocking) to stop the async executor's worker threads from stalling under concurrent slow-page fetches — `src/browser/mod.rs:91,162`

## Performance & Resource Management

**Overlap with existing FA:** Partial, but none of FA-1..5 owns this dimension directly. FA-4 notes memory is "half-wired" but frames that as an agent-loop-quality/observability gap, not a growth-bound gap. FA-3 lists "rate limiting" as a remaining safety item, which is adjacent to (but not the same as) the unbounded session/episodic-memory growth found here. FA-2's "silent no-op" finding for click/type/scroll is the reason the redundant-snapshot cost is provably wasted (the page never changes), but FA-2 itself is about honesty of results, not the duplicated-snapshot cost. No existing FA calls out the blocking-client-in-async-fn hazard, the missing session/worker eviction, or the doubled per-tool-call snapshot cost — this is genuinely new ground.

**Proposed goal:** Make the agent loop and session/worker lifecycle bounded and non-redundant: eliminate the doubled per-tool-call browser snapshot, cap every unbounded-growth container (episodic memory, sessions, workers, inbox) the same way `CrossWorkerObservations` already is, and move the blocking HTTP client off the async executor.

**Current state.** The codebase is small (~16.6k LOC Rust) and gets some things right: each `AiProvider` (Anthropic/OpenAI/Ollama) builds its `reqwest::Client` exactly once in its constructor (src/providers/anthropic.rs:15-19, mirrored in openai.rs:19 and ollama.rs:25) and reuses it across calls via `Arc<dyn AiProvider>` (src/providers/mod.rs:329-335, held in `ReActAgent.provider: Mutex<Arc<...>>` at src/agent/mod.rs:62) — no per-call client churn. `CrossWorkerObservations` (src/agent/worker.rs:187-215) is correctly bounded to a 200-entry sliding window (lines 193-201).

But the ReAct loop (src/agent/mod.rs:132-353) does structurally redundant work per tool call and several state containers grow without bound:

- `execute_with_policy`'s tool-call loop takes a full `browser.snapshot()` both before executing each tool call (agent/mod.rs:215, used only for policy evaluation) and after it (agent/mod.rs:332, used only to refresh url/title), on top of the snapshot `build_context` already took at the top of the same iteration (agent/mod.rs:457). For M tool calls in one LLM turn this is `2M+1` full snapshots when `M+1` would suffice (each tool's post-snapshot could seed the next tool's pre-snapshot).
- On the static engine, `snapshot()` (src/browser/mod.rs:266-279) clones the entire cached HTML string, then fully re-parses it (`Html::parse_document`, browser/mod.rs:268/325) and re-runs `extract_links`/`extract_images`/`extract_forms`/`extract_tables` (browser/mod.rs:343-347) — an O(document-size) DOM parse+walk repeated on every one of those `2M+1` calls even when no tool actually mutated the page (click/type/scroll are documented no-ops per FA-2, so the HTML is provably identical across those calls). On the real Tauri engine the same call pattern instead costs an IPC round trip + JS `eval` per snapshot (src-tauri/src/runtime.rs:608-636, 752-757).
- `ActionPolicy::evaluate`'s prompt-injection check (src/agent/policy.rs:361-374) builds a fresh concatenated `haystack` String from `snapshot.text` + `snapshot.html` and then `.to_lowercase()`s it (a second full-size allocation) on every one of those redundant snapshot calls.
- `EpisodicMemory::push` (src/agent/memory.rs:57-65) has no cap — every `LlmCall` and `ToolCall` event (pushed at agent/mod.rs:188-194 and 311-318 via `push_episodic`, agent/mod.rs:550-554) accumulates forever, unlike its sibling `CrossWorkerObservations` which is explicitly windowed. The whole memory is cloned wholesale on every `snapshot_state()` call (agent/mod.rs:89-93).
- `SessionManager` (src/session/mod.rs:11-173, 175-338) has `create_session` (line 39-61) inserting into `sessions: Mutex<HashMap<...>>` but no corresponding removal method anywhere in the file or the rest of the repo (confirmed via `rg -n 'sessions\.remove'` returning zero hits) — sessions, their `pages: Vec<PageHandle>`, and their `workers: HashMap` accumulate for the process lifetime. Only `close_page` (lines 136-156) removes an individual page.
- `session.inbox` (populated by `send_message`, lines 272-282) is only partially drained: `drain_inbox` (lines 286-302) re-stashes every message not addressed to the requested `worker_id` (lines 299-300) with no TTL or cap, unlike `CrossWorkerObservations`'s explicit 200-entry window.
- `BrowserEngine` performs its real network fetch with `reqwest::blocking::Client` (src/browser/mod.rs:91, built at 96-100) called synchronously inside the `async fn navigate` (line 153, `.send()` at line 162) that implements `BrowserInterface` and is invoked with `.await` from the agent loop. This is a known-enough hazard that the crate's own test suite has to route around it: the `NoopBrowser` test stub's comment explicitly says `BrowserEngine`'s blocking client "spins up its own nested Tokio runtime and panics on drop inside a `#[tokio::test]` async context" (browser/mod.rs:1277-1280).
- `AgentConfig::max_iterations` (agent/mod.rs:32, default 5 at line 39) has no upper-bound validation anywhere in the repo; combined with `build_context` cloning the whole `state.tool_results` vector every iteration (agent/mod.rs:464), a caller-supplied large `max_iterations` would make per-run cost grow O(n²) in the number of tool results, though nothing in the current call sites sets it above the default.

**Gaps:**

- **[P1]** Tool-call loop takes 2 full browser snapshots per tool call plus one in build_context (2M+1 instead of M+1), each a full HTML reparse+DOM-walk or IPC round trip — `src/agent/mod.rs:215`
  - _evidence:_ agent/mod.rs:215 (pre-exec snapshot for policy), :332 (post-exec snapshot), :457 (build_context snapshot) — three snapshot sites per tool call where one reused value would do; each snapshot is a full Html::parse_document + extract_links/images/forms/tables (browser/mod.rs:266-279,318-351) or a webview eval round-trip (runtime.rs:608-636,752-757).
- **[P1]** BrowserEngine::navigate calls a blocking reqwest client synchronously inside an async trait fn invoked with .await from the agent loop — `src/browser/mod.rs:162`
  - _evidence:_ http_client: reqwest::blocking::Client (mod.rs:91, built mod.rs:96-100) is called via self.http_client.get(url).send() (mod.rs:162) inside async fn navigate (mod.rs:153). The repo's own test comment documents the resulting hazard: 'BrowserEngine, whose reqwest::blocking::Client spins up its own nested Tokio runtime and panics on drop inside a #[tokio::test] async context' (mod.rs:1277-1280).
- **[P1]** EpisodicMemory grows without any bound, unlike its sibling CrossWorkerObservations which is explicitly windowed — `src/agent/memory.rs:63`
  - _evidence:_ EpisodicMemory::push (memory.rs:63-65) has no truncation; every LlmCall/ToolCall event is appended forever via push_episodic (agent/mod.rs:550-554, called at :188-194 and :311-318) and the whole memory is cloned on every snapshot_state() (agent/mod.rs:89-93). Contrast: CrossWorkerObservations::push (worker.rs:193-201) explicitly caps at OBSERVATION_WINDOW = 200.
- **[P1]** SessionManager never removes a session, page-vec, or worker map entry once created — no close_session/remove_worker exists anywhere — `src/session/mod.rs:39`
  - _evidence:_ create_session (mod.rs:39-61) inserts into sessions: Mutex<HashMap<String, SessionState>> (mod.rs:12,32); grep for `sessions.remove` across the repo returns zero hits. Only close_page (mod.rs:136-156) removes a single page from a session's Vec<PageHandle> — the session itself, and its workers: HashMap (mod.rs:24), live for the process lifetime, each carrying an Arc<ReActAgent> with its own unbounded episodic memory (see prior gap).
- **[P2]** session.inbox re-stashes every undelivered WorkerMessage forever with no cap or TTL — `src/session/mod.rs:299`
  - _evidence:_ send_message pushes to inbox (mod.rs:280); drain_inbox (mod.rs:286-302) partitions on worker_id and re-stashes everything not matching (`session.inbox = kept;` at mod.rs:299-300) with no size limit — unlike CrossWorkerObservations's explicit 200-entry window (worker.rs:196-200).
- **[P2]** AgentConfig.max_iterations has no upper-bound validation; combined with per-iteration full clone of tool_results, a large caller-set value is O(n^2) — `src/agent/mod.rs:32`
  - _evidence:_ max_iterations: usize (mod.rs:32, default 5 at :39) drives `for iteration in 0..max_iterations` (mod.rs:166) with no clamp anywhere in the repo; each iteration's build_context clones the entire state.tool_results Vec (mod.rs:464), so a large max_iterations makes total tool_results cloning cost O(n^2) in the number of accumulated results.
- **[P2]** Prompt-injection scan does two full-page-size allocations (concat + to_lowercase) on every tool-call policy check, multiplied by the redundant-snapshot gap above — `src/agent/policy.rs:374`
  - _evidence:_ snapshot_contains_prompt_injection (policy.rs:361-374) builds a new haystack String from snapshot.text + snapshot.html then calls .to_lowercase() (line 374) — two O(page-size) allocations per call, run once per tool call via ActionPolicy::evaluate (policy.rs:182), so it inherits the 2x-per-tool-call redundancy from the snapshot-duplication gap above.

**Top actions:**

- (high leverage) Collapse the tool-call loop's duplicate snapshots in execute_with_policy: reuse each tool's post-execution snapshot (agent/mod.rs:332) as the next tool call's pre-execution snapshot (agent/mod.rs:215) instead of re-fetching, and reuse build_context's snapshot (agent/mod.rs:457) for the first tool call in the iteration — cuts snapshot count from 2M+1 to M+1 per iteration on both the reparse-based and IPC-based engines. — `src/agent/mod.rs`
- (high leverage) Move BrowserEngine::navigate's blocking reqwest::blocking::Client::send() call off the async executor via tokio::task::spawn_blocking, or replace the field with the same async reqwest::Client pattern already used by the providers (built once in the constructor). — `src/browser/mod.rs`
- (high leverage) Cap EpisodicMemory::push with the same sliding-window pattern already implemented for CrossWorkerObservations (200-entry window) — a small, low-risk diff that reuses an in-repo precedent. — `src/agent/memory.rs`
- (med leverage) Add SessionManager::close_session and a worker-removal method so the sessions/workers maps don't grow forever, and bound session.inbox the same way CrossWorkerObservations is bounded — needed before FA-1's planned long-running daemon can run unattended. — `src/session/mod.rs`

## Developer Experience &amp; API Ergonomics (README/docs honesty, public Rust API surface, examples, error-message quality for programmatic callers)

**Overlap with existing FA:** Adjacent to FA-1 (Programmatic Surface): FA-1's "stabilized library API" outcome presumes there is a documented, trustworthy Rust API to stabilize - this audit shows the current docs describing that API (SKILL.md, AGENT-SURFACE.md) are themselves wrong, which FA-1 does not call out. The specific "12 documented tools vs 17 registered tools, 5 missing" fact is already precisely tracked in docs/specs/programmatic-surface-design-2026-07-20.md:221 and is the basis of FA-2's "5 of 12 advertised tools have no working Rust path" - true overlap there, cited as corroboration only. The dead-ToolError finding is already tracked in docs/goals/optimization-backlog-2026-07-20.md:159-162 (not one of FA-1..5, but pre-existing) - also corroboration, not new. The SKILL.md fictional-builder-API finding, the near-zero rustdoc coverage, the missing examples/ directory, and the README env-var scope ambiguity are not mentioned in any FA or backlog file I checked and are the net-new contributions of this audit.

**Proposed goal:** Make NeuroBrowser's public API and docs trustworthy for a first-time programmatic caller: every code example in SKILL.md/AGENT-SURFACE.md/README compiles against the real API, every re-exported public item carries a doc comment, and a runnable examples/ target exists - so FA-1's "stabilized library API" has something honest left to stabilize.

**Current state.** NeuroBrowser is a single Rust library crate (src/lib.rs:1-32, re-exporting ~40 public items: ReActAgent, ActionPolicy, SessionManager, BrowserEngine, ToolRegistry, ToolError, etc.) plus a separate Tauri wrapper crate (src-tauri/).
