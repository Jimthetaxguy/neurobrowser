## Prior-art resolutions (act on these)

### `AIAnytime/agent-browser` — name collision, not an ancestor
REAL but trivial, and NOT a fork of vercel-labs/agent-browser — a pure name collision. Verified from the report's direct source reads (github.com/AIAnytime/agent-browser + commits page): 2 total commits both dated 2025-07-13, 22 stars / 17 forks / 0 issues / 0 PRs, MIT license, TS 57% / CSS 21% / JS 10% / Rust 10%. It is a one-day dormant Tauri v2 + React + Node.js teaching demo of the plain-text ReAct pattern (Thought/Action/Observation/Final Answer). Critically, its four 'tools' (search_dom/click_button/scrape_table/extract_prices) are hardcoded placeholder strings in the Rust run_tool_and_wait command — there is NO wired DOM/WebView automation, so it is illustrative, not functional. No memory, no policy layer, no daemon. It shares no git history, no code, and no owner with vercel-labs/agent-browser (Apache-2.0, 85.6% Rust, ~38.8k stars, real CDP automation). ACTION FOR NB: correct any docs that conflate the two 'agent-browser' repos — cite them as two distinct, unrelated projects. AIAnytime is at best a loose 'earlier ReAct-shape reference,' not an architectural ancestor.

## Differentiation thesis (lead with these)

- Policy-native autonomy that can be SCORED: NB is the only surveyed system shipping a 3-level ActionPolicy + per-domain allow/deny + sensitive-arg redaction + prompt-injection detection together. Lead with an ST-WebAgentBench-style Completion-under-Policy + Risk Ratio benchmark — a differentiated quality axis WebArena/Mind2Web/WebVoyager/BrowserGym literally do not measure.
- Real native OS webview per page (WKWebView/WebView2/WebKitGTK) instead of embedded/pinned Chromium — full-fidelity JS rendering, ~50MB footprint, OS-vendor-patched-for-free, and genuine multi-engine coverage no single-engine competitor tests. The tradeoff (live-site DOM drift across three engines) becomes a marketed strength via a per-engine verification matrix + live-site eval subset.
- Local-first, no-telemetry privacy as an enforced property, not a slogan: pair the claim with network-layer request blocking/mocking tools so 'no trackers' is verifiable at runtime, not just asserted.
- Owns the full webview integration (not embedded Chromium), uniquely positioning NB to adopt forward-looking page-declared tool discovery (WebMCP) and a hardened, explicitly-named WRY IPC bridge with message-origin validation wired into the injection detector.
- A headless daemon exposing the SAME atomic 12-tool surface plus a tabs-as-workers model over Unix socket/TCP — a clean substrate for policy-scoped, per-connection tool profiles that most OSS agent libraries (single-session, single-tab) cannot match.

## Ranked net-new features

### [P0] NB-1 — Native dialog handling tool
- **What:** Add handle_dialog (accept/dismiss/respond-with-text) covering window.alert/confirm/prompt/beforeunload to the agent surface, expanding it from 12 to 13 tools.
- **Why:** Outright correctness bug today: Tauri child webviews route native JS dialogs to OS-level modal dialogs that block the whole ReAct loop indefinitely. Any page calling alert() silently hangs the agent. Cheapest highest-impact fix in the backlog.
- **Shape:** Register a per-tab dialog handler on the WKWebView/WebView2/WebKitGTK bridge that intercepts the native callback, queues a pending-dialog state exposed to the agent, and resolves it via the new tool call under ActionPolicy (default auto-dismiss at ReadOnly).

### [P0] NB-2 — Explicit @eN ref-invalidation contract
- **What:** Document and enforce that @eN refs are scoped to the snapshot that produced them and become invalid on navigate/reload/re-snapshot, returning a typed StaleRef error instead of acting on a wrong element.
- **Why:** Correctness AND safety: acting on a stale ref after the page changed defeats the point of ActionPolicy gating actions on current page state. playwright-mcp (ref) and chrome-devtools-mcp (uid) both enforce this; NB should match.
- **Shape:** Tag each snapshot with a monotonic snapshot_id; store it in the ref map; every interaction tool checks the live tab's current snapshot_id and returns Err(StaleRef{expected,got}) on mismatch. Bump the id on any navigation/DOM-replacing event.

### [P0] NB-3 — Credential broker + named vault (unified secret handling)
- **What:** Store secrets locally keyed by name; extend type_text/submit_form to accept {credential_ref: "name"} so raw values are resolved inside the Rust core and never enter the LLM prompt, transcript, memory, or logs. Gate decryption on ActionPolicy tier.
- **Why:** Merges vercel-labs' named vault with Skyvern/Dia's credential-broker pattern. Strictly stronger than NB's current output-side redaction, which still requires the secret to pass through tool-call args before being scrubbed. Closes the residual leak surface entirely.
- **Shape:** New CredentialStore in core (OS keychain-backed or AES-256-GCM file, env-supplied key). A resolve-at-execution seam in the tool dispatcher swaps credential_ref->plaintext just before the webview form-fill call; the ReAct layer only ever sees the ref.

### [P0] NB-4 — Plan-preview / approval checkpoint before Assisted+ execution
- **What:** Before executing a multi-step tool-call sequence at Assisted or HighAutonomy tiers, surface the generated ordered plan (tool calls + target refs + human-readable element descriptions) for inline edit/approve.
- **Why:** Mirrors Fellou Deep Action and Skyvern's schema+stop-code contract. Gives a single checkpoint to catch a misread instruction before any side-effecting action, without forcing ReadOnly for every task. Directly leverages NB's existing tier system.
- **Shape:** Insert an optional plan-emit phase in the ReAct loop that streams a proposed action list as a new agent-event type, pauses on a policy-gated approval gate, and resumes/edits/aborts based on the user's response before the first side-effecting tool runs.

### [P0] NB-5 — Versioned JSON TaskSpec catalog + neurobrowser-eval harness
- **What:** Define a TaskSpec schema (id, start_url, goal, policy_tier, domain_class, webview_engine tags, eval descriptor [dom_query|url_match|llm_judge]) and a driver crate/CLI that runs the real 12-tool ReAct loop headlessly against each task, using NB's own query_selector/get_text/evaluate as the DOM-state checkers, writing JSONL traces + pass/fail + policy-violation flags. Seed ~50-100 tasks (WebArena-verified subset + Mind2Web cross-task split + NB-native daemon/swarm tasks).
- **Why:** Closes the biggest gap named across the whole survey: NB has 8 ad-hoc integration tests and no task catalog while every competitor benchmark ships hundreds. Turns 'does the agent still work' into one command with machine-readable, diffable output. Foundation for NB-6.
- **Shape:** tests/task_catalog/*.json read by a neurobrowser-eval crate; a `trait EvalTask { setup(); goal(); eval(trace)->TaskResult }` (BrowserGym-style) standardizes tasks over one ReAct-loop driver; evaluators are Rust closures over existing tool outputs; runs land in runs/<id>/{trace.jsonl,result.json,screenshots/} reusing the streaming-event schema.

### [P0] NB-6 — Completion-under-Policy + Risk Ratio scoring
- **What:** Score every catalog task on two axes from ST-WebAgentBench: (1) goal completed AND declared ActionPolicy tier + per-domain rules respected (CuP), and (2) on a seeded prompt-injection subset, did the injection detector correctly flag/refuse (Risk Ratio analog). Break out pass-rate by policy_tier, not just aggregate.
- **Why:** NB's single most defensible published metric — it is the ONLY surveyed system with a built-in 3-level policy engine + injection detector, and no other benchmark (WebArena/Mind2Web/WebVoyager/BrowserGym) scores this axis at all. This is the differentiation lever, made measurable.
- **Shape:** Extend TaskResult with policy_violations[] and (for the injection subset) detector_outcome; score = task_success && zero_violations; add a seeded injected-content task class scored on detector trigger rate. Report a tier x pass-rate table in CI.

### [P1] NB-7 — Structured diagnostics envelope for tool results
- **What:** Wrap evaluate/get_text/navigate/wait_for/extract_text outputs in a typed diagnostics object (fetch_errors, js_exceptions, console_messages, error_kind), modeled on fastrender's RenderDiagnostics, instead of free-text error strings.
- **Why:** Lets the ReAct loop's LLM branch on structured failure categories (network fail vs JS exception vs selector-not-found) rather than pattern-matching stringified errors, materially improving agent self-correction reliability. Also the smallest useful slice of chrome-devtools-mcp's diagnostics breadth.
- **Shape:** Define a ToolDiagnostics struct returned alongside every tool result; populate console/exception fields from the webview bridge's console + error hooks; expose an error_kind enum the loop can match on.

### [P1] NB-8 — Cookie / storage + network interception tools
- **What:** Add get/set/delete/clear tools for cookies + localStorage/sessionStorage, and route/unroute-style request blocking + mocking by URL pattern.
- **Why:** Two gaps in one: storage tools unlock auth-session reuse and state hydration the 12-tool surface cannot do at all; network interception turns 'local-first, no telemetry' into an enforced runtime property (block trackers at the network layer) rather than a claim. Both are table-stakes across playwright-mcp/chrome-devtools-mcp.
- **Shape:** Bridge cookie/storage tools to each engine's native store APIs; implement route/unroute over the webview's request-interception hook (WKURLSchemeHandler / WebView2 WebResourceRequested / WebKitGTK resource-load signals), with patterns gated by ActionPolicy.

### [P1] NB-9 — Fuel-budgeted JS execution for the evaluate tool
- **What:** Bound agent-issued evaluate() calls with an operation-count fuel budget plus a wall-clock secondary timeout, following fastrender's vm-js model, so a runaway or injected script cannot hang a tab even at HighAutonomy.
- **Why:** Real gap: ActionPolicy + injection detection gate what an agent may REQUEST, but nothing bounds the COST of a script once allowed to run. Engine-level fuel is a second, independent line of defense.
- **Shape:** Wrap injected scripts in an instrumented harness that increments a counter on a coarse op boundary and aborts on budget/wall-time breach; return a typed BudgetExceeded diagnostic (ties into NB-7).

### [P1] NB-10 — Encrypted session/profile persistence tier
- **What:** Add an AES-256-GCM-encrypted session-state file (cookies + web storage, env-supplied key) with auto-save on tab close + periodic idle checkpoints, layered onto the three-tier memory model and gated by ActionPolicy.
- **Why:** vercel-labs ships this; NB's context describes no persistence/encryption story for auth state. Concrete gap for any logged-in-session-continuity workflow, and it composes with NB-3's vault and NB-8's storage tools.
- **Shape:** Serialize the webview's cookie/storage snapshot to an encrypted blob next to the native store; restore on tab spawn when policy permits; reuse the CredentialStore key infra.

### [P1] NB-11 — Per-role LLM split (planner vs actor)
- **What:** Extend the pluggable-provider config so the high-level planning step and the per-step tool-selection/action step each bind to independently configured providers/models (Nanobrowser's Planner/Navigator split).
- **Why:** Route expensive reasoning to a strong model while running a cheap/fast model on the repetitive per-step loop — cost efficiency without sacrificing plan quality. NB already has the provider abstraction; this is a config + loop-wiring change, not new infra.
- **Shape:** Split the single provider handle into {planner, actor} in the loop config; default both to the same provider for back-compat; thread the role into each LLM call site.

### [P1] NB-12 — Tool-profile scoping on the headless daemon
- **What:** Let the Unix-socket/TCP daemon accept a --tools / policy-tier parameter per connection so a ReadOnly client only sees a minimal read tool set, not just gets denied at runtime.
- **Why:** Defense-in-depth by construction (mirrors agent-browser's --tools core|all): an untrusted lower-trust caller literally cannot see write/navigate tools, shrinking prompt-injection blast radius. Natural fit for NB's existing per-connection daemon model.
- **Shape:** Map policy tier -> allowed tool-name set at connection handshake; filter the advertised tool manifest and reject out-of-profile calls before dispatch.

### [P1] NB-13 — Goal-decompose swarm mode over tabs-as-workers
- **What:** Add an orchestration layer: one LLM call decomposes a user goal into N domain-diverse, non-overlapping sub-tasks (hyperswarm's explicit source-diversity heuristic); each dispatches to a tabs-as-worker running the existing ReAct loop in parallel under ActionPolicy; a final LLM pass synthesizes all outputs. Include a single 'stop all' cancellation.
- **Why:** NB's tabs-as-workers is the ideal substrate for the decompose->fan-out->synthesize pattern proven by hyperswarm. Turns broad multi-source research from a sequential slog into a parallel op finishing in the time of the slowest worker.
- **Shape:** New agent mode: decompose(goal)->[subtask{domain}]; spawn N workers via the existing tab/worker registry; stream per-tab events; add a fan-out AbortSignal 'stop all' daemon command over the worker registry; synthesize(results) as a final call.

### [P1] NB-14 — Provider/policy CI gate against real models + rotating live-site subset
- **What:** A nightly/pre-merge CI job running a ~20-30 task catalog subset against real Anthropic/OpenAI/Ollama providers under a budget cap (cached-response replay fixtures for fast PR iteration), plus a small rotating set of real low-risk live sites (Online-Mind2Web methodology) to catch DOM drift.
- **Why:** Satisfies the real-systems-only principle (no shipping on mocks) and tests NB's actual architectural differentiator — real native webview per page is uniquely exposed to live-site layout drift a Docker-replay suite would never surface.
- **Shape:** Reuse NB-5 harness; add a budget-capped real-provider mode with replay fixtures for local runs; a separate live-site lane scored by an LLM-judge, isolated from the deterministic fixture catalog used for PR gating.

### [P0] NB-15 — WRY IPC-bridge hardening spec + WebMCP page-tool discovery
- **What:** Formally document NB's postMessage/custom-protocol bridge between Rust core and the webview JS context, with explicit message-origin validation wired into the prompt-injection detector so page content cannot spoof tool-bridge messages. Separately, support pages that declare their own MCP tool manifest (chrome-devtools-mcp's execute_webmcp_tool/list_webmcp_tools).
- **Why:** Two forward-looking, ownership-enabled items: the bridge is NB's actual attack surface today and is unnamed/unhardened; WebMCP is a differentiator NB is uniquely positioned to exploit because it owns full webview integration rather than embedding Chromium.
- **Shape:** Add origin/nonce validation on every inbound bridge message and feed failures to the injection detector as events; for WebMCP, detect a page-declared manifest and expose its actions as callable tools under ActionPolicy.

### [P1] NB-16 — Cached action memoization + vision fallback for element resolution
- **What:** Persist successful (@eN element -> action) resolutions keyed by domain + DOM-fingerprint in semantic memory; replay cached actions first, re-invoking the LLM snapshot only on cache miss or drift (Stagehand self-healing). When ref lookup fails, fall back to a vision-LLM pass over a screenshot to relocate the element by description (Skyvern hybrid) before failing.
- **Why:** Directly hardens NB's ref-based @eN model — its known fragility is markup drift between runs. Cuts LLM cost/latency on repeat visits and reduces brittle failures on dynamic/obfuscated DOMs, the exact resilience edge vision+DOM hybrids have over pure-ref systems.
- **Shape:** Cache layer in semantic-memory tier keyed by domain+DOM hash; on miss, take a screenshot and run a vision pass to map the described target back to a live ref; instrument cache hit-rate for the eval harness.

### [P2] NB-17 — Session observability + live screencast for HighAutonomy
- **What:** Optional local read-only HTTP dashboard (agent-browser's port-4848 pattern) showing live tab/worker state, recent tool calls, and ActionPolicy decisions; plus a screencast_start/stop stream so a human can watch a HighAutonomy session in real time.
- **Why:** Real-time human observability is a stronger safety story for autonomous tiers than after-the-fact log review, and builds the trust needed before users grant HighAutonomy. Pairs naturally with the tabs-as-workers model and the plan-preview checkpoint (NB-4).
- **Shape:** Small local HTTP server in the daemon subscribing to the existing streaming-event bus; a screencast channel emitting frames (ideally via a shared-memory transport) that the dashboard renders.

### [P2] NB-18 — Engine Adapter abstraction layer
- **What:** Introduce a trait-based EngineAdapter between the 12-tool agent surface and the rendering backend so Tauri/WRY stays default but a future Servo-FFI (or Blitz) backend can be swapped without changing the agent-facing tool contract. Split the core along Blitz-style seams (dom-query / paint-or-screenshot / network / window-shell).
- **Why:** Keeps NB's rendering strategy reversible. Servo (92.7% WPT, LF Europe backing, v0.3.0) is the only credible non-webview Rust engine maturing toward embeddability, and Verso already proved the 'Servo as Tauri webview backend' thesis — an adapter lets NB track that maturation without a ReAct-surface rewrite.
- **Shape:** Define `trait EngineAdapter { snapshot(); query(); click(); evaluate(); screenshot() }`; implement WryAdapter first; refactor core crates along dom-query/paint/network/shell boundaries so backends swap behind one interface.

## Supporting gaps surfaced by the code audit


### P0 (3)
- **Migrate to native provider function/tool-calling instead of text-parsed actions** (agent-loop) — Neither AnthropicProvider::complete (src/providers/anthropic.rs:64-125) nor OpenAiProvider::complete (src/providers/openai.rs:27-108) sends a `tools`/function-calling schema to the API. Both send a single system+user message pair and then run the returned free-text content through parse_tool_calls (src/providers/mod.rs:106-139), which regex-splits on literal lines like 'ToolCall: {...}' or 'Action: name(args)'. This is fragile: it depends on the model choosing to emit exactly that string pattern (which build_system_prompt only teaches via a plain-text convention, mod.rs:295-296) rather than using the provider's native structured tool-call mechanism (Anthropic tool_use blocks, OpenAI tool_calls array), which both APIs support and which the existing ToolRegistry.definitions() (src/tools/mod.rs:207-209) could feed directly.
  - shape: Add a `tools: Vec<ToolDefinition>` (from ToolRegistry.definitions()) to AiContext; in anthropic.rs pass a `tools` array built from those definitions and read `content` blocks of type `tool_use` instead of calling parse_tool_calls; in openai.rs pass `tools` in the request body and read `choices[0].message.tool_calls`; keep parse_tool_calls only as a fallback for providers/models without tool-calling support (e.g. some Ollama models).
- **Surface real interactive-element data (selectors) to the model, not just counts** (agent-loop) — PageSnapshot already carries structured, selector-bearing data -- LinkInfo.selector, FormInfo.selector, FormInputInfo.selector (src/tools/mod.rs:136-164) -- but build_context (src/agent/mod.rs:473-481) collapses all of it into a bare count string ('Links: 3\nImages: 1\nForms: 2'), and that string is never even read by build_system_prompt (src/providers/mod.rs:274-317). The model is therefore asked to call tools like click(selector) or type(selector, text) without ever being shown a single real selector on the page.
  - shape: Add a bounded (e.g. top-N by viewport position or relevance) rendering of page_info.links/forms/images with their .selector and .text/.href into the prompt, either as a new AiContext field consumed by build_system_prompt, or folded into dom_snapshot and then actually wiring dom_snapshot into build_system_prompt. Needs a token-budget cutoff since real pages can have hundreds of elements.
- **Native provider tool-calling / structured outputs** (providers) — None of the three providers use each API's native JSON-schema tool-calling: OpenAI's `tools`/`tool_choice` chat-completions params, Anthropic's `tools` array + `tool_use` content blocks, or Ollama's `/api/chat` `tools` field. All three instead rely entirely on the free-text `parse_tool_calls` scraper (mod.rs:106-228) driven by a plain-English system-prompt convention (build_system_prompt, mod.rs:295-296: "ToolCall: {...}"). Confirmed by grep across src/: no occurrence of `tools`, `tool_choice`, `function_call`, or `tool_use` request/response handling anywhere in src/providers/, and no `ToolCall::parse_native`-style function exists.
  - shape: Map the existing browser tool registry (crate::browser::default_tool_registry(), already used by mod.rs's positional_argument_names) to each provider's native tool-definition JSON schema; pass it as `tools` on each request; read tool_use/tool_calls blocks directly from the response instead of calling parse_tool_calls. Keep the text-based parser only as a fallback for models/providers without structured tool-calling support (e.g. small local Ollama models).

### P1 (15)
- **No distinct plan/act/reflect phases in the ReAct loop** (agent-loop) — execute_with_policy (src/agent/mod.rs:166-338) is a single flat loop: build_context -> provider.complete -> (final answer OR execute every returned tool_call in sequence) -> next iteration. There is no separate 'planning' call that lays out a multi-step approach before acting, and no dedicated 'reflection' step that evaluates a tool result against the original goal before deciding the next action -- the same completion call that decides to act also implicitly stands in for both. This is confirmed structurally: there is exactly one 'Reflect' mention in the file and it is a comment about copying a URL field (mod.rs:330), not an actual reflection stage.
  - shape: Add a `Plan` variant to AgentRunEvent (src/agent/policy.rs) emitted once per run from an initial planning-only provider call (no tools offered); thread the resulting plan text into AiContext (src/providers/mod.rs) as a new field consumed by build_system_prompt; add a lightweight post-tool-result reflection call only when a tool fails or when finish_reason suggests uncertainty, gated behind a config flag so the default flat loop remains available for cheap/fast runs.
- **Generate the LLM-facing tool list from ToolRegistry instead of a hardcoded string** (agent-loop) — build_system_prompt (src/providers/mod.rs:295-315) hardcodes 17 tool descriptions as string literals ('navigate(url): ...', 'click(selector): ...', etc.) in parallel with the real ToolRegistry that ReActAgent actually dispatches through (agent/mod.rs:497-500) and that already exposes a `.definitions()` method (src/tools/mod.rs:207-209) nobody calls. The file already contains a defensive patch for this drift risk -- positional_argument_names() (providers/mod.rs:217-228) re-derives real argument order from the registry specifically because the hardcoded prompt text and the tool's real parameter names can disagree.
  - shape: Have build_system_prompt take a `&[ToolDefinition]` (from registry.definitions()) and render name/description/arguments from that, deleting the hardcoded tool list; requires threading the registry (or its definitions) into AiContext or into build_system_prompt's call site.
- **True incremental/token-level streaming** (streaming-worker) — execute_stream (src/agent/mod.rs:561-640) runs the full ReAct loop to completion via execute_with_policy, then replays the resulting Vec<AgentRunEvent> over the channel post-hoc (the code's own comment at mod.rs:568-571 admits this: 'full incremental streaming is tracked for a follow-up').
